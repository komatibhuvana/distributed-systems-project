The Challenge of Reliable Cloud Messaging

  • Cloud systems must guarantee message delivery ("At-Least-Once")
  • Network failures cause retransmissions → extra load
  • The Gap: Existing models assume "Exponential" service times
  • Reality: Real workloads are "Heavy-Tailed" (Pareto)
  • Rare, huge jobs can block the entire queue
Analogy: Think of a DMV where one person needs 4 hours of paperwork — everyone behind them waits!

Li et al. (2015) - Message Queueing in Cloud

  • Models cloud message brokers (like AWS SQS)
  • Uses Colored Petri Nets (CPN) for formal verification
  • Key model: Two-stage "Tandem Queue"
  • Assumes M/M/N queueing (exponential service times)
  • Derives formulas for latency, queue length, utilization
Paper Title: "Modeling Message Queueing Services with Reliability Guarantee in Cloud Computing Environment Using Colored Petri Nets"

Two-Stage Tandem Queue Architecture

Publishers → [Stage 1: Broker] → Network → [Stage 2: Receiver] → Consumers

              (n₁ servers, μ₁)    (D, p)    (n₂ servers, μ₂)

Key Insight

Stage 2 sees HIGHER traffic due to retransmissions!

Traffic Inflation Formula

Λ₂ = λ / (1 - p)

If p=20% failure → Stage 2 sees 25% more traffic

Why "Heavy Tails" Matter

Exponential (M/M/N)

  • Most jobs similar size
  • Predictable behavior
  • Like Starbucks orders

Pareto (M/G/N)

  • Most jobs small
  • Rare HUGE jobs exist
  • Like DMV paperwork
Real Examples:
• Web requests: Most 100ms, video processing 10s
• Database queries: Most 10ms, complex joins 5s

Three Approaches to M/G/N Queues

Problem: No exact closed-form solution exists!

Method Best For Error Range
Kingman (1961) Low variability 5-15%
Whitt (1993) ⭐ High utilization 3-10%
Allen-Cunneen Heavy tails 5-12%
Recommendation: Use Whitt (1993) as default
